# Phase 09 (standalone): GPU histogram build performance — row-partition + register-batching

## Goal

Ship the two complementary GPU-build levers the spikes validated, in the ONE place the
resident/batched LDS launch geometry is decided (`resident_raw_build_into`), without touching
the CPU f64 anchor or the existing small-shape parity gates.

- **Lever 1 — row-partitioning (spike-007, VALIDATED ~1.35×):** the production
  `construct_leaf_hist_resident_lds_kernel` launches `CubeCount = (num_features, 1)` — one
  workgroup per feature, which starves a 96-CU gfx1100 on large leaves. Add a row-partition `P`
  so each feature's rows split across P cubes (LightGBM's `grid_dim_y`). Tune to ~8 wkgrps/CU;
  **never maximize** (spike showed P=32 over-partitions and regresses).
- **Lever 2 — register row-batching (todo, LightGBM `NUM_DATA_PER_THREAD=400`):** fold K rows per
  loop iteration so the hardware pipelines the scattered bin-reads. Measured add-on; complementary
  to Lever 1 (occupancy × per-cube ILP).

## Why this is safe (the parity argument — READ FIRST)

The spike found row-partitioning raises GPU-vs-anchor f32 divergence from ~4e-7 to **~2e-5
relative at 1M rows** (each partition is an independent f32 partial-sum tree). That EXCEEDS the
existing `max_rel < 1e-5` LDS test gate. The phase stays safe because:

1. **P is gated to large leaves.** `row_partition_count()` returns **1** below a row threshold
   (≥ the GPU-win zone, well above the 8k-row test shapes and the `RESIDENT_MIN_NUM_DATA=12_000`
   resident gate). So every existing parity test (n=8k, 30k, 50k) runs the **byte-identical P=1
   path** and is unaffected.
2. **The CPU f64 anchor is the merge gate and is untouched.** Only the f32 GPU kernel changes.
3. **The new divergence is documented, not hidden** — a new large-shape test asserts a relaxed,
   commented tolerance and 04-ROCM-GAPS records the residual. This matches the project contract:
   *"the ~1e-6 GPU-vs-CPU parity contract at large shapes is a separate, still-open gate"*
   (spikes/MANIFEST Requirements).

<steps>
1. Add a `row_partition_count(num_features, leaf_rows) -> u32` helper in histogram.rs:
   - Returns `1` when `leaf_rows < ROWPART_MIN_LEAF` (large-leaf threshold; default ~256_000,
     env-overridable `LGBM_ROWPART_MIN` for benching) OR when `num_features >= TARGET_CUBES`.
   - Else `P = clamp(TARGET_CUBES / num_features, 1, P_MAX)` with `TARGET_CUBES ≈ 8 * CU_count`
     (gfx1100 = 96 → ~768) and `P_MAX` ~16 (spike sweet spot; 32 regressed). Document the constants
     with the spike-007 numbers.
2. Add the `p`/`np` strided-row dimension to BOTH `construct_leaf_hist_resident_lds_kernel` and
   `construct_leaf_hist_batched_lds_kernel`: `let p = CUBE_POS_Y; let np = CUBE_COUNT_Y;` start
   `k = p*cd + UNIT_POS`, stride `np*cd`. The zero + merge passes are unchanged (every cube of a
   feature merges its sub-hist into the same global slot — additive, order-free). P=1 ⇒ identical
   to today.
3. In `resident_raw_build_into` (and the batched launcher `build_leaf_histograms_batched_f32_on`),
   compute `P = row_partition_count(num_features, rows)` and launch
   `CubeCount::Static(num_features, P, 1)`. Naive (>256-bin) fallback path stays P-less.
</steps>
<acceptance_criteria>
- `cargo build --release --features rocm` clean.
- With `LGBM_ROWPART_MIN` forcing P=1, the resident build output is **bit-identical** to the
  pre-change build (add a debug assert or a one-shot test capturing this).
- `row_partition_count` unit-tested (CPU, no GPU) for the boundary cases: small leaf → 1,
  many features → 1, large leaf + few features → P in [2, P_MAX], never > P_MAX.
</acceptance_criteria>
</task>

## Out of scope (seeds for later)

- **16-bit discretized histogram** (`.planning/seeds/16bit-discretized-histogram.md`) — separate
  parity story; pull forward only when atomic *width*, not occupancy, is the bottleneck.
- Multi-feature-per-cube packing (LightGBM `block_dim_x` over columns) — a different decomposition;
  not needed if row-partitioning saturates the GPU.
- ROI note: CPU is multi-threaded (spike-005) and beats GPU at every tested size — this is
  **ROCm-parity-track** perf, not overall-fastest. Land it as parity-path improvement.
