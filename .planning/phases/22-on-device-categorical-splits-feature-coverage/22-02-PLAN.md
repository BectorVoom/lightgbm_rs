<objective>
Add the additive categorical metadata that the §6.3 bitset construction and §8.1 evaluator
need but which `GrowFeature` deliberately omits today (grow_driver.rs:45-46 explicitly excludes
`bin_to_category` "which the on-device numeric grow loop does not consume this milestone").

This plan is pure plumbing — it adds fields and populates them in the test harness helper. It
does NOT wire the categorical branch (that is plan 22-04). Keeping the field extension in its
own Wave-1 plan lets the transcription (22-03) and wiring (22-04) build on a settled struct.

Two edits:
1. **`GrowFeature` += 6 native fields** (grow_driver.rs:50): `bin_to_category: Vec<i32>`,
   `cat_smooth: f64`, `cat_l2: f64`, `max_cat_threshold: i32`, `max_cat_to_onehot: i32`,
   `min_data_per_group: i32`. Native primitives ONLY — importing any `lgbm-treelearner`/
   `lgbm-dataset` type would create the crate cycle (RESEARCH A3 / memory
   `on-device-driver-crate-cycle-constraint`).
2. **`grow_features_of` (learner_parity.rs:1982)** populates those fields from the `GainConfig`
   categorical scalars and the `FeatureColumn.bin_to_category` the `cat_corpus` builder already
   carries (learner_parity.rs:1470). For numeric features `bin_to_category` is empty and the
   scalars take their config defaults — the numeric structure gate must stay byte-identical.

Purpose: unblocks 22-03 (the evaluator reads these scalars) and 22-04 (the wiring reads
`bin_to_category` for SetRealThreshold). SC #4: numeric path byte-unchanged.
Output: an extended `GrowFeature` + a harness helper that fills it, both compiling with the
numeric driver tests still green.
</objective>
