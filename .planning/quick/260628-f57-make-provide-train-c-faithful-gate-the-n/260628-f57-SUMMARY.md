# Quick 260628-f57 — SUMMARY

## What shipped
Made `booster.rs` training-metric evaluation **C++-faithful**: it no longer
force-evaluates the training metric on every iteration just because there is no
`eval_set`. `crates/lgbm/src/booster.rs:1291`:

```rust
- let provide_train = config.is_provide_training_metric || valid.is_none();
+ let provide_train = config.is_provide_training_metric;
```

This matches gbdt.cpp (default `is_provide_training_metric=false` ⇒ empty training
history) and removes the ~26% host-side waste spike-048 found on Kaggle CUDA
(~4.5s/100 trees at 500k×50, identical on the CPU run ⇒ pure host cost).

## Why it was safe (the divergence was test-encoded)
Four `lgbm` unit tests and the multiclass parity-cell builder trained WITHOUT a
valid set yet asserted training-metric `eval_history`, relying on the old clause.
They were realigned to the explicit C++ opt-in `.is_provide_training_metric(true)`
— restoring their exact prior behavior. The parity **goldens are unchanged**: they
already contained per-round training `multi_logloss`; the harness config just now
requests it explicitly.

Sites changed:
- `crates/lgbm/src/booster.rs` — core fix + 4 test builders
  (`public_api_train_predict_round_trip`, `metric_freq_thins_eval_history`,
  `custom_metric_feval_matches_builtin_l2`, `custom_metric_nan_is_typed_error`).
- `crates/oracle-harness/tests/boosting_parity.rs` — `multiclass_cell_builder`
  (feeds `multiclass_metrics` + `multiclassova_metrics`).

## Verification (all on the default CPU build / warm cache)
- `cargo test -p lgbm` → **41/41**.
- `cargo test -p oracle-harness --test boosting_parity` (the hard merge gate) →
  **75/75** (incl. `multiclass_metrics`, `multiclassova_metrics`).
- `cargo test --workspace` → **0 failures**.
- Shipped-path confirmation (`LGBM_PHASE_PROF=1`, no eval_set, default config):
  `metric` phase **6.08ms → 0.000ms** — the per-iter training-metric eval is gone.

## Impact
- Default `train()` / Python `LGBMClassifier.fit()` without `eval_set` no longer
  pays the per-iter training-metric cost — the ~23% CUDA win spike-048 proved via
  `metric_freq`, now the default, parity-neutral to the trees.
- Behavior now matches official `lightgbm` (`evals_result_` empty without
  `eval_set` + default config).

## Caveats / follow-ups
- Python wheel NOT rebuilt here (heavy). The Rust-level path is verified; if any
  Python test asserted non-empty training history without `eval_set` it would need
  updating to match official (none found in source grep). Flagged for the Python
  suite on next wheel build.
- The remaining ~52% of the spike-048 gap is the architectural GPU tree-learning
  long-pole (host-orchestrated per-leaf launches) — out of scope here.
