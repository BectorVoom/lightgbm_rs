<objective>
Eliminate the thread contention found in quick 260620-9cp. There, a parallel cross-feature scan
`par_iter` contended with the already-parallel feature build `par_iter` (Spike-005,
`build_leaf_histograms_raw`, `crates/lgbm-compute/src/lib.rs:562`): an isolated-scan −13% win
inverted into a +11% warm train-wall regression because two competing parallel regions made
threads partition twice and thrashed cache.

Fix the root cause: for the directly-built (smaller / root) leaf, do per-feature
`{build histogram → fix_histogram → scan}` inside ONE rayon region. Threads partition over
features ONCE, and each feature's histogram stays cache-hot in the SAME thread that built it
through fix and scan — no hand-off, no second fork/join. This is the **host f64 analog of the
existing GPU fusion** (`build_fix_scan_resident`, RocmBackend, `crates/lgbm-compute/src/lib.rs`
~769-831; `#[cube]` kernel `crates/lgbm-compute/kernels/histogram.rs:2444`), which already fuses
the whole chain into ONE launch per feature for the directly-built leaf. On CpuBackend
`resident_pool_supported()` returns false, so the fused gate is OFF and the CPU path takes the
TWO-STEP (`build_leaf_histogram_into` then `scan_leaf_histogram`). This task brings the fusion
to the host f64 path.

Project #1 non-negotiable: **bit-exact CPU f64 parity with the C++ reference**. Each feature is
independent (disjoint histogram region, own ascending-leaf_rows / grad-at-`bin<<1` fold order, own
`fix_histogram` with RAW sums + most_freq_bin compaction, own scan). Co-locating build+fix+scan
for one feature on one thread changes NEITHER per-feature operation order NOR the cross-feature
argmax (still serial, in feature order, after the region) — bit-exact by the same
per-feature-independence argument that makes the existing parallel build and the 9cp parallel scan
bit-exact (both proven green under forced parallelism).

Two prior NULLs whose mistakes must not repeat: 8v4 (per-call 2-lane fork/join, ~13× slower) and
9cp (cross-feature scan par_iter contending with the parallel build → +11% train-wall regression).
The decisive metric is therefore **warm end-to-end train-wall**, not the isolated SCAN_NS counter.
Honest NULL (keep serial two-step default, document why) is a fully acceptable outcome.

Purpose: Recover the isolated-scan locality win without the cross-region contention that erased it.
Output: A gated unified `build_fix_scan` region for the directly-built leaf's spine numeric
features, an A/B measurement, and a hard parity gate.
</objective>
