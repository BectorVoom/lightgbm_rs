<objective>
Extend the unified host fusion landed in quick 260620-a48 (the directly-built "smaller"
child: per-feature {build → fix → scan} in ONE rayon region, `CpuBackend::build_fix_scan_impl`,
`crates/lgbm-compute/src/lib.rs:1290`) to the **subtract-derived "larger" child**.

Today the host larger-child chain (`learner.rs:1633-1676`, the `parent_slot.is_some()` host
branch) is a two-step: `subtract_histograms(parent, smaller) → owned derived Vec →
copy_from_slice(larger_slot)`, then a SEPARATE `scan_leaf_histogram(... unified=false ...)`.
This plan fuses **subtract → scan** into ONE rayon `par_iter` over features, gated exactly
like a48.

Why this should WIN where the standalone parallel-scan (9cp) was NULL: the larger child has
NO parallel build region (its only pre-scan work is a cheap element-wise subtract), so 9cp's
build/scan contention is STRUCTURALLY ABSENT; and the larger child is ~half of all leaves, so
this roughly doubles a48's coverage. Crucially: the larger child is NOT re-FixHistogram'd
(non-negotiable #3 — C++ runs no FixHistogram on the use_subtract larger child), so the fused
chain is just subtract → scan (NO fix) — simpler than a48's build → fix → scan.

Purpose: capture the isolated −13% wide scan win on ~half the leaves WITHOUT contention.
Output: a gated `CpuBackend::subtract_scan`, a `larger_unified` learner gate, an honest A/B
verdict, and a bit-exact CPU f64 parity proof on both default and forced-on modes.

NON-NEGOTIABLE: bit-exact CPU f64 parity with the C++ reference. A NULL A/B is acceptable;
a manufactured win is not.
</objective>
