# Phase quick Plan b97: Extend unified fusion to the subtract-derived larger child — Summary

Fused the subtract-derived **larger** (use_subtract) child's per-feature `{subtract → scan}`
into ONE rayon region (`CpuBackend::subtract_scan`, NO build, NO fix), mirroring a48's
`build_fix_scan_impl` for the directly-built smaller child. **Verdict: WIN**, adopted gated
at a **separate threshold of 130** (env `LGBM_UNIFIED_SUBSCAN_THRESHOLD`), leaving a48's
smaller-unified default at 100 untouched.

## What was done

- **Task 1 (`7ebbaac`)** — `Backend::subtract_scan` trait method (default typed error) +
  `CpuBackend` override delegating to the inherent `subtract_scan_impl`: hoisted per-feature
  `[slot_off, slot_off+2*num_bin)` range validation against parent/smaller/larger
  (deterministic lowest-index `LengthMismatch`), ONE rayon `par_iter` computing each
  feature's private region `parent[start..end] − smaller[start..end]` (the exact cell-wise
  op of `subtract_histograms` over the disjoint range — NO fix; non-negotiable #3) then
  `find_best_split` if spine-active, order-preserving serial assembly into `larger_buf`.
  Learner: `larger_unified` gate (`!resident_eligible && parent_slot.is_some() &&
  subtract_audit.is_none() && features.len() >= threshold`); when set the seam materializes
  owned parent/smaller scratch (aliasing-safe: `parent_slot == larger_slot`) and
  `scan_leaf_histogram` routes the spine scan through `subtract_scan` via a new
  `subtract_inputs` param (reusing Pass-1's exact gating). 3 RED→GREEN unit tests.
- **Task 2 (`4b5bf8a`)** — A/B (below), adopted WIN at a separate `unified_subscan_threshold()`
  (default 130).
- **Task 3** — HARD CPU f64 parity merge gate run in BOTH modes (counts below).

### Verdict: WIN, separate threshold = 130

The larger child crosses to a **sign-stable** (no-run-overlap) train-wall gain at ≥130 feat;
at 120 feat the gain is real but distributions overlap. The crossover (~130) is **materially
higher** than a48's smaller-child threshold (100) — the larger child's single rayon fork/join
over subtract+scan only amortizes above ~130 features — so per the plan a **separate**
`LGBM_UNIFIED_SUBSCAN_THRESHOLD` (default **130**) is justified. a48's smaller-unified default
stays **100**. The overlapping 120-feat zone keeps the byte-unchanged two-step path; ≥130 takes
the fused path. Both adoption gates met (wide sign-stable gain AND no narrow regression). This
is the structurally-expected outcome: the larger child has NO parallel build to contend with
(only a cheap serial subtract), so 9cp's contention is absent — but that same absence means the
isolated subtract+scan fork/join amortizes only at higher feature counts than a48's
build+fix+scan.

## Deviations from Plan

- **[Design choice, not a deviation]** The plan's action sketched calling `subtract_scan` at
  the SEAM and threading a `larger_unified` flag into the scan that "must NOT re-scan". The
  implementation instead runs the fused `subtract_scan` INSIDE `scan_leaf_histogram` (the seam
  only materializes the parent/smaller scratch and passes it via a new `subtract_inputs`
  param). This is strictly more faithful to a48's contract: it reuses Pass-1's exact
  spine-gating to build `scan_active`, so the precomputed scan-active splits line up
  byte-identically with `batched_feats` downstream — eliminating the risk of re-deriving the
  spine gate at the seam. Net behavior is identical to what the plan intended (splits flow from
  the fused subtract→scan, not a second scan). Proven bit-exact forced-on.
- **[Threshold]** Introduced a SEPARATE `LGBM_UNIFIED_SUBSCAN_THRESHOLD` (default 130) rather
  than reusing `unified_bfs_threshold()` — the A/B showed the larger child's crossover (~130)
  is materially higher than a48's 100, which the plan explicitly permits ("introduce a separate
  LGBM_UNIFIED_SUBSCAN_THRESHOLD only if the larger child's crossover differs materially").
