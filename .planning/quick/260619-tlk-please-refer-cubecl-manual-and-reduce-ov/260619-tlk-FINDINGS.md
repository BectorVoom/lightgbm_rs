## 1. cubecl 0.10 manual — the overhead-reduction idioms (cited)

Fetched via `ctx7 docs /tracel-ai/cubecl` (the `/tracel-ai/cubecl` library; High reputation).
Source attributions are the cubecl repo `README.md` and `cubecl-book/`. The runtime API
shapes are quoted from the resolved `cubecl-runtime-0.10.0/src/client.rs`.

### 1a. `launch_unchecked` — drop in-kernel bounds-check codegen

> "calling the autogenerated `launch_unchecked` function" — `README.md` (Launch CubeCL
> Kernel on a Device). The `#[cube(launch_unchecked)]` macro generates a typed launch
> that elides the per-access bounds-check codegen; the caller takes on the safety
> obligation (`cubecl-book` "Macros: #[cube] and #[cube(launch)]"; runtime
> `execute_unchecked` carries `# Safety: Without checks, the out-of-bound reads and
> writes can happen.`, `cubecl-runtime-0.10.0/src/client.rs`).

**Production state:** SHIPPED across all 8 rocm histogram kernels + the split/partition
hot paths (quick 260619-nrw). The 2 CPU f64-anchor kernels deliberately stay
`#[cube(launch)]` (bit-exact gate). Benched (260619-ol8): NULL for the atomic-class
kernels (contention/launch-fixed-cost bound), real (~9–16% launch-bound, ~40–46%
compute-bound) only for the fused single-unit f64 path — which is already wired. **No
remaining `launch_unchecked` lever.**

### 1b. `read_one` / `read_one_unchecked` — the single-handle drain

Quoted verbatim from `cubecl-runtime-0.10.0/src/client.rs` (lines 131–149):

```rust
pub fn read(&self, handles: Vec<Handle>) -> Vec<Bytes> {
    cubecl_common::reader::read_sync(self.read_async(handles)).expect("TODO")
}
pub fn read_one(&self, handle: Handle) -> Result<Bytes, ServerError> {
    Ok(cubecl_common::reader::read_sync(self.read_async(vec![handle]))?.remove(0))
}
pub fn read_one_unchecked(&self, handle: Handle) -> Bytes {
    cubecl_common::reader::read_sync(self.read_async(vec![handle]))
        .unwrap()
        .remove(0)
}
```

**Load-bearing fact:** `read_one_unchecked(h)` is *defined as* `read_async(vec![h])`
drained by `read_sync` — i.e. it is **literally the one-element case of the batched
`read(Vec<Handle>)`**. Both route through the identical `read_async(handles) → read_sync`
drain. So for a launcher that produces ONE consolidated out-handle, `read_one_unchecked(h)`
and `read(vec![h])` are the *same single deferred drain*; there is no N-handle read loop
for the batched idiom to collapse. (This is the equivalence the audit example demonstrates.)

### 1c. Batched `client.read(Vec<Handle>)` — collapse an N-handle read loop into ONE drain

The manual's idiomatic multi-output drain is `client.read(handles: Vec<Handle>)` — a single
`read_async` over all handles followed by one `read_sync`. Its overhead win is *only*
realised when the alternative is an **N× `read_one` loop** that pays N separate
`read_async → read_sync` round-trips. (This is the win the prior q2z/sgu thread recorded
as bench-only — see §3.)

### 1d. Deferred / lazy execution — submission is decoupled from synchronization

> "due to the asynchronous nature of GPUs" … "`sync()` … blocks until all GPU work is
> done" — `cubecl-book` (Benchmarking reduction / the `Benchmark` trait). Kernel launches
> are submitted asynchronously; the device sync happens at a `read`/`sync`/`flush` point
> (`client.flush()` "Flush all outstanding commands"; `client.sync()` "Wait for the
> completion of every task in the server" — `cubecl-runtime-0.10.0/src/client.rs`).

**Implication:** the lazy-execution lever (submit N launches back-to-back, then ONE
deferred drain) only pays off when there are **N independent launches that would otherwise
each be followed by an immediate blocking read**. If a path already collapses to ONE launch
+ ONE read, deferral has nothing to defer.

### 1e. Allocation reuse — `client.empty` / `client.create_from_slice`

> "Buffer management is explicit and efficient using methods like
> `client.create_from_slice`, `client.empty`, and `client.read_one`" — `cubecl-book`
> (Summary). `client.empty(size)` "Reserves `size` bytes … and returns a handle"
> (`cubecl-runtime-0.10.0/src/client.rs`).

**Production state:** the device-resident bin matrix is uploaded ONCE
(`upload_resident_columns`, histogram.rs:2023) and reused for every leaf; the histogram
pool is device-resident across leaves (no per-leaf re-upload of bins). The only per-leaf
host→device uploads are the small `leaf_rows` + gathered `grad/hess` + zeroed outputs.
**No redundant per-call re-upload remains** (the per-call re-upload tax was the mwr finding,
already eliminated by the resident model).

### 1f. Autotune — runtime kernel/config selection

> "Autotuning drastically simplifies kernel selection by running small benchmarks at
> runtime … combines gracefully with comptime" — `cubecl-book` (core-features/autotune).
> Configured via `GlobalConfig`/`AutotuneConfig` (`cubecl-book` advanced-usage/config).

**Applicability:** autotune chooses among *alternative kernels/configs*; it is not an
overhead-elimination lever for an already-single-launch path. It is orthogonal to this
task's "reduce round-trips" ask and out of scope (it would only matter if we had multiple
competing histogram kernels to pick between at runtime; the row-partition `P` is already
fixed analytically, 260619-007). Recorded for completeness, not pursued.

## 2. PRODUCTION round-trip inventory (launcher-by-launcher)

Method: every `::launch*` and `read_one_unchecked`/`client.read` in
`crates/lgbm-compute/src/{kernels,lib}` was enumerated (grep, see commit), then each
launcher classified PRODUCTION (reachable from the `lgbm-treelearner` learner via a wired
`Backend` method) vs TEST-ONLY (only oracle-harness / rocm parity tests / examples call it).

### 2a. What the learner actually drives per leaf (the hot path)

`crates/lgbm-treelearner/src/learner.rs` per-leaf split path (≈ lines 1503–1700 +
2026–2089), cross-referenced with the wired `RocmBackend` methods in
`crates/lgbm-compute/src/lib.rs`:

- **Directly-built leaf (`fused_build`):** ONE call to `backend.build_fix_scan_resident`
  (lib.rs:1384) → `build_fix_scan_resident_f64_on` (histogram.rs:2444). That function
  issues **ONE launch** (`build_fix_scan_fused_kernel::launch_unchecked`,
  `CubeCount::Static(n,1,1)` — one cube per feature, **ALL features in a single launch**:
  build → fix → compact → scan) and **ONE consolidated read** (`read_one_unchecked(h_out)`,
  histogram.rs:2677) that returns only the small per-feature SplitInfo cells (`n*12` f64).
  The full histogram Handle `h_hist` **stays resident** (stored into the pool slot — NO
  readback).
- **Subtract-derived larger child:** ONE call to `backend.subtract_resident`
  (lib.rs:1319) → `subtract_histograms_f64_from_handles_on`. Device-resident:
  parent − smaller → larger, result Handle stored back in the pool. **NO readback.** Then
  ONE `backend.scan_resident_leaf` (lib.rs:1356) → `find_best_splits_batched_fused_f64_from_handle_on`:
  ONE fused scan launch over the resident Handle, ONE consolidated SplitInfo read.
- **CPU-fallback batched path (no resident pool):** `backend.find_best_splits_batched`
  (lib.rs:563) → per-feature `find_best_split`; this is the non-resident fallback, not the
  gfx1100 resident training path.

### 2b. Standalone launcher round-trip table (PRODUCTION launchers)

| Launcher (fn) | Launches issued | Out-handles left unread before sync | Read calls | Resident output? |
|---|---|---|---|---|
| `build_fix_scan_resident_f64_on` (hist.rs:2444) — **per-leaf hot path** | **1** (all features, 1 cube/feature) | 0 (hist stays resident) | **1** `read_one_unchecked` (SplitInfo cells only) | YES (`h_hist` → pool) |
| `subtract_histograms_f64_from_handles_on` (via `subtract_resident`, lib.rs:1319) | 1 | 0 | **0** (result Handle stays resident) | YES |
| `find_best_splits_batched_fused_f64_from_handle_on` (via `scan_resident_leaf`) | 1 | 0 | **1** (SplitInfo cells) | reads resident Handle |
| `build_fix_compact_resident_f64_on` (hist.rs:2062) | 1 | 0 | 1 | YES |
| `subtract_histograms_f64_on` (hist.rs, std subtract) | 1 | 0 | 1 | NO |
| `find_best_split_f64_on` / `find_best_splits_batched_fused_f64_on` (split.rs) | 1 | 0 | 1 (SplitInfo) | NO |
| `data_partition` kernel (partition.rs:253) | 1 | 0 | 1 (`h_route`) | NO |

**Every production launcher is one-launch → at-most-one-consolidated-read.** None leaves
≥2 out-handles unread before a sync. The per-leaf path is the single fused
`build_fix_scan_resident` launch + a device-resident subtract (no readback) + one small
SplitInfo drain.

## 4. VERDICT — CASE A: no remaining non-redundant production lever

**The production GPU dispatch/read path already satisfies every cubecl-0.10 overhead-
reduction idiom the user pointed at.** Evidence:

1. **`launch_unchecked` (§1a):** shipped on all production GPU kernels; the only kernel
   where it measurably pays (the fused f64 single-unit path) is already wired.
2. **Batched `client.read(Vec<Handle>)` (§1c) / single-handle `read_one_unchecked`
   (§1b):** every production launcher emits ONE consolidated out-handle and reads it with
   ONE `read_one_unchecked`. By the runtime source (§1b), `read_one_unchecked(h)` *is*
   `read(vec![h])` — the same single `read_async → read_sync` drain. There is **no
   N-handle read loop** anywhere in the production read path for the batched idiom to
   collapse (§2b/§2c). The batched form's win regime (an N× `read_one` loop) does not
   exist in production.
3. **Deferred / lazy execution (§1d):** the per-leaf path is ONE fused launch + a device-
   resident subtract (no readback) + one small SplitInfo drain. There are no N independent
   per-feature launches each followed by an immediate blocking read to defer (that pattern
   is TEST-ONLY, §2c). Nothing to defer.
4. **Allocation reuse (§1e):** the resident bin matrix + histogram pool are uploaded once
   and reused across leaves; only the tiny per-leaf `leaf_rows`/`grad`/`hess`/zeroed-output
   handles are created per leaf. No redundant re-upload.

**Therefore there is NO genuinely-new, non-redundant batched-read / deferred-sync /
round-trip-elimination lever remaining in the production dispatch/read path.** Manufacturing
a per-handle read loop just to "beat" it with the batched idiom would re-introduce a pattern
production already beats (the q2z/sgu anti-pattern) — explicitly forbidden by this task and
by "Faithfulness over busy-work." No production change is made.

The audit example `batched_read_audit_ab.rs` (Case A confirmation harness) demonstrates the
manual-predicted equivalence on gfx1100: for the production shape (ONE consolidated
out-handle per launcher), `read_one_unchecked(h)` and the batched `read(vec![h])` are the
same single drain (no measurable, sign-stable separation — they are the same code path with
a one-element Vec), so there is no N-handle loop to collapse.
