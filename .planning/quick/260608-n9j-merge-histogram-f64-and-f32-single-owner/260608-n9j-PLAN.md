# Quick Task 260608-n9j: Merge histogram f64/f32 single-owner fold into one shared #[cube] helper

The structural "merge" analog of the split work (260608-mc5's `split_scan_body`), scoped by the
user to the SHARED-HELPER-ONLY option. `construct_hist_kernel` (f64 cells, histogram.rs:40-57) and
`construct_hist_kernel_f32` (f32 cells, histogram.rs:66-81) are explicitly "SAME single-owner
ordered fold, SAME row order — the ONLY difference is the accumulation cell type" (comment at :60,
:73). Today that fold loop is duplicated in two `#[cube(launch)]` kernels — a drift hazard. Collapse
the duplication into ONE generic-over-`Numeric` `#[cube]` helper; both launch kernels become thin
wrappers that call it. Zero algorithmic/perf change; single source of truth.

## Out of scope (DO NOT TOUCH)
- The PARALLEL f32-atomic kernels `construct_hist_kernel_atomic_f32` (:294) and
  `construct_leaf_hist_batched_kernel` (:380) — they use `Atomic<f32>::fetch_add`, a DIFFERENT
  algorithm (nondeterministic order, the ~1e-6 ROCm gate). They cannot share the bit-exact fold
  helper and are not part of this merge.
- `construct_histograms_cpu_native` (the R2 native production CPU path) — leave as-is (per the
  mc5 lesson, cubecl-cpu loses to native; CpuBackend keeps native).
- Host launchers, V5 validation, the Backend trait, the learner.

Add a private generic helper:

```rust
#[cube]
fn hist_fold_body<N: Numeric>(
    binned: &Array<u32>,
    grad: &Array<f32>,
    hess: &Array<f32>,
    out: &mut Array<N>,
) {
    // Single-owner ordered fold — the deterministic anchor (Pitfall 1).
    if UNIT_POS == 0 {
        for i in 0..binned.len() {
            let ti = binned[i] as usize * 2;
            out[ti] += N::cast_from(grad[i]);     // f32 read, N-cell accumulate
            out[ti + 1] += N::cast_from(hess[i]);
        }
    }
}
```

Then make `construct_hist_kernel` (f64) and `construct_hist_kernel_f32` (f32) thin wrappers that
call `hist_fold_body::<f64>(...)` / `hist_fold_body::<f32>(...)`. Keep their public
`#[cube(launch)]` signatures, names, and doc comments (the capability-gate routing depends on the
two named launch entry points). For N=f64, `N::cast_from(grad[i])` is identical to the current
`f64::cast_from(grad[i])` (widening f32→f64); for N=f32 it is the identity cast == current
`out[ti] += grad[i]` — so BOTH paths are byte-identical to today.

Use the correct cubecl import for `Numeric`/`CubeType` bound and `cast_from` (mirror how
`split_scan_body` / gain.rs generic #[cube] fns declare their bounds). If a `#[cube]` helper cannot
be generic over `Numeric` in this cubecl version, fall back to a macro or two-type duplication that
STILL removes the hand-written loop divergence — but try the generic helper first.
