<objective>
Merge the FORKED split-finding implementations (native-Rust CPU `find_best_split_cpu_native` vs cubecl `find_best_split_kernel`) into ONE generic-over-runtime `#[cube]` scan that BOTH backends run, THEN collapse `find_best_splits_batched` from one launch per (feature) to ONE launch per LEAF so the unified cubecl path is fast on both CpuBackend (cubecl-cpu) and RocmBackend (cubecl-hip).

This unifies the single source of truth for the REVERSE+FORWARD scan math and delivers the deferred per-leaf launch-count collapse from quick task 260608-lsx (whose `find_best_splits_batched_f64_on` is still a per-feature loop-of-launches, split.rs:825-869).

Purpose: A single shared scan removes the maintenance hazard of two transcriptions drifting; the fused kernel makes a unified cubecl path viable by amortising dispatch cost across all features in one launch (the reason R2 went native was per-CALL launch overhead).

Output: a shared `#[cube]` scan helper, a fused batched f64 kernel + launcher (`find_best_splits_batched_fused_f64_on`), both backends wired through it, an oracle assertion proving fused == per-feature == native bit-exact, and a before/after CPU + GPU perf measurement.

NON-NEGOTIABLE (CLAUDE.md): CPU f64-fold bit-exactness is the hard merge gate. If the unified cubecl-cpu path regresses CPU wall-clock materially EVEN AFTER batching, that is a real finding — surface it honestly and recommend CpuBackend keep `find_best_split_cpu_native` (merge the GPU launches only), rather than shipping a silent CPU slowdown. Do NOT weaken any tolerance; the f32 hip-split path and its D-03a gap (04-ROCM-GAPS.md) are OUT of scope.
</objective>
