<objective>
SPIKE-FIRST / INVESTIGATE-ONLY. Probe the ONE genuinely un-measured-in-isolation
GPU histogram overhead mechanism: cubecl LAZY EXECUTION (manual ch.05). Today every
per-feature histogram launcher in `histogram.rs` does `launch_unchecked` immediately
followed by a BLOCKING `client.read_one_unchecked(h_out)` — so across all features in
a leaf the CPU submit serializes with GPU execute (submit → block → submit → block …).
The manual's lever is to decouple submission from synchronization: submit all N
per-feature launches back-to-back (CPU never blocks), then issue ONE deferred
`read_one` at the end that drains the whole queue.

This plan creates a SINGLE new rocm-gated A/B example that measures:
- **Arm A (current pattern):** N × { upload + launch into a fresh `out` handle + IMMEDIATE `read_one_unchecked` }.
- **Arm B (lazy / deferred sync):** N uploads + N launches into N distinct `out` handles submitted back-to-back, then ONE `read_one_unchecked` at the end (reading every handle, the last read forcing the full queue to drain).

The arms differ ONLY in WHEN the device sync happens. A device-resident binned buffer
is reused so the A/B isolates the sync/dispatch pattern, not transfer.

Purpose: an honest, reproducible measurement + disposition of whether deferring the
sync across a leaf's per-feature launches recovers launch/submit overhead. Given the
heavy prior art (c2l: launch-bound not transfer-bound; nn7/oib: round-trip elimination
"mixed win"; ol8: launch_unchecked NULL for atomics; nrw: launch_unchecked already
shipped) the HONEST expectation is NULL/modest — a benched NULL kept as a primitive is
a valid outcome (cf. p93, ol8). NO production kernel is modified and nothing is wired.

Output: `crates/lgbm-compute/examples/lazy_dispatch_ab.rs` (the rocm-gated A/B example)
and `260619-q2z-FINDINGS.md` (the measurement + disposition).
</objective>

Structure (mirror `launch_unchecked_ab.rs` and `plane_aggregate_ab.rs` exactly):

1. A `#[cfg(not(feature = "rocm"))] fn main()` stub that prints the "requires --features
   rocm (gfx1100)" message and returns — so the CPU-only build compiles with zero rocm
   codegen.

2. A `#[cfg(feature = "rocm")] fn main()` body. Imports: `cubecl::prelude::*`,
   `lgbm_compute::runtime::{probe_capabilities, rocm_client}`, the per-feature production
   kernel `lgbm_compute::kernels::histogram::construct_hist_kernel_atomic_f32` (the
   shipped `#[cube(launch_unchecked)]` kernel — confirm it is `pub`; if it is not exported,
   inline a byte-identical `#[cube(launch_unchecked)]` twin in the example with a SYNC
   WARNING doc comment exactly like launch_unchecked_ab.rs's twins, copying the body from
   histogram.rs lines ~388 — `out[bin*2].fetch_add(grad[idx]); out[bin*2+1].fetch_add(hess[idx])`
   guarded by `idx < binned.len()`). This lever needs no plane, but DO
   `probe_capabilities(&client)` and print it for the record.

3. Module doc block (`//!`) explaining: WHAT THIS QUANTIFIES (the un-benched lazy-execution
   lever — N per-feature launches each followed by an immediate blocking read_one, vs N
   launches submitted back-to-back then ONE deferred read_one; the manual's exact ch.05
   pattern); the EXPECTED-NULL framing citing the prior art (c2l launch-bound-not-transfer;
   ol8 launch_unchecked NULL for atomics; the lever payoff scales with launches/leaf so
   feature-count is a PRIMARY axis); MEASUREMENT-ONLY (no production change); the
   WARM-VS-COLD discipline (WARMUP discard, MEDIAN + p25/p75, INTERLEAVED arms, RE-RUN
   across >=2 process restarts); and "this is a MANUAL rocm bench — NOT a test gate".

4. `median` and `spread` (p25/p75) helpers copied from the existing harnesses.

5. A `assert_same_input_f32` same-input correctness helper (ABS 5e-6 + REL 1e-5, copied
   from launch_unchecked_ab.rs): arm A and arm B must produce IDENTICAL per-feature
   histograms (deferring the sync must not change numerics). This is the correctness
   column. NOTE in a comment that this is a same-input drift guard, NOT the parity gate
   (the parity gate is the CPU f64 anchor; this f32-atomic path is GPU-vs-GPU same-input).

6. Deterministic generators: a feature-major `gen_resident(feats, num_data, num_bin) -> Vec<u32>`
   bin matrix and `gen_grad`/`gen_hess` copied from launch_unchecked_ab.rs (the device-
   resident binned buffer that BOTH arms reuse, so transfer is held equal — upload the
   resident bin matrix ONCE per cell, OUTSIDE both timed arms, exactly like
   launch_unchecked_ab.rs kernel-2/3).

7. The A/B sweep. PRIMARY axes = FEATURE-COUNT (the launches/leaf knob — the lever's
   payoff scales with it) AND bin-count. Use a feature sweep `FEATS_SWEEP = [8, 32, 128]`
   and a `BIN_SWEEP = [16, 64, 256]`, across two leaf-size regimes:
     - launch-bound: small leaf (e.g. num_data 4_096, leaf_n 1_024, warmup 15, timed 21) —
       where per-launch submit/sync cost dominates and the lever is most likely to show.
     - compute-bound: large leaf (e.g. num_data 200_000, leaf_n 200_000, warmup 3, timed 7) —
       where GPU execute dominates and the lever should wash out.
   For each (regime, feats, bins) cell:
     - Build `feats` per-feature binned columns by slicing the resident matrix
       (`resident[f*num_data .. f*num_data + leaf_n]`), one grad/hess pair shared (the
       gathered ord_g/ord_h to leaf length, like the LDS cells).
     - **Arm A (immediate-sync, current pattern):** for f in 0..feats { create the f's out
       handle (zeros, len 2*num_bin), launch `construct_hist_kernel_atomic_f32::launch_unchecked`
       into it, then IMMEDIATELY `client.read_one_unchecked(h_out_f)` and collect → Vec<f64>.
       Reuse the already-uploaded resident bin handle + a shared grad/hess handle so ONLY
       the per-feature out handle is fresh (transfer held equal across arms).
     - **Arm B (deferred-sync, lazy):** allocate a Vec of `feats` distinct out handles up
       front; for f in 0..feats issue `construct_hist_kernel_atomic_f32::launch_unchecked`
       into out-handle[f] WITHOUT reading; AFTER the launch loop, `read_one_unchecked` each
       of the `feats` handles (the deferred drain — the last read forces the full queue to
       complete). Collect identically to arm A.
     - SAFETY comment on each `launch_unchecked`: binned/grad/hess sized leaf_n, idx<len
       guarded in-kernel, every bin<num_bin keeps out[bin*2+1] in range, out sized 2*num_bin
       — same host-proven obligations as the shipped `construct_histograms_parallel_f32_on`.
     - INTERLEAVE the arms per timed iter (time arm A, then arm B, in the same loop body),
       after `warmup` interleaved untimed iters. Force the device sync INSIDE each timed
       call by including the read_one(s) in the timed region (arm A's reads are inline; arm
       B's deferred reads are inside the timed block too — the whole point is that arm B
       pays ONE drain at the end vs arm A's N drains).
     - Concatenate each arm's per-feature histograms into one Vec<f64> for the same-input
       assert (A vs B must match within the f32 envelope).
     - Compute `delta% = (a_med - b_med) / a_med * 100` (>0 ⇒ arm B / lazy faster) and print
       a table row: regime, feats, bins, a_ms, b_ms, delta%, a p25/p75, b p25/p75.

8. A trailing LEGEND/notes block (copy the style of the existing harnesses): delta>0 ⇒
   deferred-sync faster; a delta within the p25/p75 spread or sign-flipping across restarts
   is SUB-NOISE / NULL; RE-RUN across 2-3 process restarts; the same-input asserts passing
   ⇒ deferring the sync is numerically identical; MEASUREMENT ONLY.

Do NOT place fenced code blocks anywhere in this action — write the example as ordinary
Rust source in the file. Match the comment density and tone of plane_aggregate_ab.rs.
