<objective>
Parallelize the row-reorder inside `DataPartition::split` (`crates/lgbm-treelearner/src/data_partition.rs`) with rayon, mirroring C++'s `ParallelPartitionRunner` (`schedule(static, 512) if (num_data_ >= 1024)`), so the tall-narrow CPU training gap closes WITHOUT breaking the bit-exact merge gate.

Root cause (measured this session, `.planning/notes/wide-tall-two-backend-root-cause.md`): at 1M rows x 50 features the Rust CPU trainer is ~1.7x C++ per-iteration and `DataPartition::split` is 29.2% of train wall while single-threaded; at wide shapes it is ~5% (dwarfed by the 500-feature build), so this lever is tall-shape-specific.

Purpose: convert the serial per-leaf-row gather/scatter into a deterministic chunked prefix-sum parallel reorder that is byte-identical to the current output (the partition order is load-bearing for the histogram subtraction trick and the row->leaf map). Gate it on a leaf-row threshold so small leaves never pay fork/join cost (the spike-005 regression class).

Output: a parallel `split` with a `split_parallel_equals_serial` bit-exactness test, leaf-row gating via a new env knob, and an end-to-end before/after bench at the tall-narrow shape proving the win is real.
</objective>

  <action>
    First add `rayon = "1.10"` to `[dependencies]` in `crates/lgbm-treelearner/Cargo.toml` (copy the exact version string from `crates/lgbm-compute/Cargo.toml`, which already declares `rayon = "1.10"`). This crate does NOT yet depend on rayon — `lgbm-compute` does, but `lgbm-treelearner` has no rayon entry today, so it must be added. No other new dependency.

    Then rewrite the numeric (non-categorical) `split` body (currently the serial gather at lines ~129-133 of `data_partition.rs`, the `backend.data_partition` call, and the serial scatter-back at ~148-150) so that for leaves at/above a row threshold it parallelizes the reorder with rayon, and below the threshold it runs the EXISTING serial path verbatim.

    Bit-exact parallel design (mirror C++ ParallelPartitionRunner, `data_partition.hpp:101-119`, which static-chunks the rows, gathers per-chunk left/right buffers, then prefix-sum-concatenates them — this is the C++ approach the task mandates, NOT an order-nondeterministic scatter):
    1. Take the leaf's current `indices_[begin..begin+count]` global row ids (these stay the per-row order to preserve).
    2. Compute the per-row routing decision identically to `data_partition_cpu_native` (`kernels/partition.rs`): `th = threshold + min_bin` (`-1` if `most_freq_bin == 0`); `default_to_right = most_freq_bin > threshold`; a row goes RIGHT iff (`bin < min_bin || bin > max_bin`) ? `default_to_right` : `bin > th`, where `bin = feature_bins.bin(global_row)`. Keep the same V5 validation the backend op performs (`num_bin > 0`, `threshold < num_bin`, every per-row `bin < num_bin`) and surface the SAME `ComputeError` for the SAME lowest-index offending row so the parallel error order matches the serial path (validate before the parallel region, walking rows ascending — the pattern documented for `find_best_splits_batched` in `lgbm-compute/src/lib.rs`).
    3. Split `[begin..begin+count]` into fixed static chunks (chunk size 512 to mirror C++ `schedule(static, 512)`; a contiguous ascending partition so chunk order is deterministic). For each chunk in parallel, produce its left-row global ids (in ascending within-chunk order) and its right-row global ids (in ascending within-chunk order), plus the chunk's left-count and right-count.
    4. Exclusive-prefix-sum the per-chunk left-counts to get each chunk's left write offset (base `begin`), and exclusive-prefix-sum the per-chunk right-counts to get each chunk's right write offset (base `begin + total_left`). total_left = sum of all chunk left-counts = the serial `split_point`.
    5. Scatter each chunk's left ids and right ids into `indices_[..]` at its prefix-summed offsets (chunks write DISJOINT regions, no atomics). Because chunk order is ascending and within-chunk order is preserved, the final `[all left | all right]` is byte-identical to the serial stable two-pass gather — assert this in the test.
    6. Set `left_count = total_left as i32`, `right_count = count - left_count`, and update `leaf_count[leaf]`, `leaf_begin[right_leaf]`, `leaf_count[right_leaf]` exactly as today.

    Because the parallel path now computes routing inline, the `backend.data_partition` call is no longer needed on the parallel branch; keep the existing serial branch calling it (or the inline serial equivalent) so behavior below threshold is unchanged. Do NOT change `split_categorical`, the GPU/resident path, or any signature/public API. Do NOT change anything in the categorical branch.

    Add a leaf-row gate `par_split_threshold()` reading env `LGBM_PAR_SPLIT_THRESHOLD` (parse-or-default), defaulting to 16384 — the same default and idiom as `par_build_threshold()`/`LGBM_PAR_THRESHOLD` in `lgbm-compute/src/lib.rs` (so small/medium leaves stay serial, avoiding the spike-005 fork/join regression; per the C++ `if (num_data_ >= 1024)` guard intent). `count < threshold` => serial path verbatim.

    Do NOT inline fenced code in the action; follow the structural design above and the cited C++/native-kernel sources for exact arithmetic.

    Add the `split_parallel_equals_serial` test (described in <behavior>) under the existing `#[cfg(test)] mod tests`, mirroring `build_histograms_parallel_equals_serial` in `lgbm-compute/src/lib.rs`: scattered global rows, deterministic hash-generated bins, force-parallel (threshold env = 0) vs force-serial (threshold env = usize::MAX), assert the written `indices_in_leaf` slices are byte-identical. Guard env-var get/set so the two existing split unit tests are unaffected (set+remove within the new test, or read the override once into a local).
