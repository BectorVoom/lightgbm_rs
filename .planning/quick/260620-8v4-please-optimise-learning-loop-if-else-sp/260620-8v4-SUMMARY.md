# Phase quick-260620-8v4: Optimise the learning-loop split-scan kernel Summary

**Audited the 2-lane (REVERSE ∥ FORWARD) split-scan lever end-to-end: the SCAN is a material 44.3% of per-leaf compute on the wide config (GO gate cleared), so the additive 2-lane variant was built and proven bit-exact — but A/B measurement shows it is ~13x SLOWER (rayon fork/join overhead per us-scale per-(feature,leaf) call), so the verdict is a documented NULL/regression; the serial path stays the unchanged default and bit-exact source of truth.**

## What was done

- **Task 1 (measurement, GO/NO-GO gate):** built `bench_split_scan.rs` (a new
  `lgbm-treelearner` example) that drives the full per-leaf BUILD/SCAN hot path
  through the facade `lgbm::train` and reads the existing
  `phase_prof::{BUILD_NS, SCAN_NS}` counters (`LGBM_PHASE_PROF=1`). Warm window
  (cold iteration discarded), `cubecl-cpu` f64 anchor, narrow (10 feat) + wide
  (120 feat). Result (2 stable runs): **narrow SCAN ≈ 34-35%, wide SCAN ≈ 44.3% ≥
  20% ⇒ GO.**
- **Task 2 (apply the verdict — GO branch):** added `find_best_split_cpu_native_2lane`
  (split.rs) as an **additive** alternative to the serial `find_best_split_cpu_native`.
  Each pass is byte-for-byte its serial counterpart; the two run on `rayon::join`
  lanes, combined by a strict-`>` cross-lane argmax that reproduces the serial
  keep-first-on-tie winner (REVERSE wins ties) bit-for-bit. Gated behind
  `LGBM_SPLIT_2LANE=1` in `CpuBackend::find_best_split` (OFF by default). Proven
  bit-exact (2 new unit tests). **A/B: ~13x slower scan ⇒ NULL.** Wrote FINDINGS.md
  with verbatim numbers.
- **Task 3 (HARD parity merge gate):** ran the four authoritative CPU f64 anchor
  suites — all bit-exact / green (verbatim below), both with the default serial
  path AND with `LGBM_SPLIT_2LANE=1` active (the additive path is also bit-exact
  through the full learner).

## A/B result (the NULL — verbatim medians)

| Config | Serial SCAN | 2-lane SCAN | SCAN ratio | Serial warm_wall | 2-lane warm_wall | wall ratio |
|--------|------------:|------------:|-----------:|-----------------:|-----------------:|-----------:|
| narrow | ~34.1 ms  | ~464 ms  | ~13.6x slower | ~170.7 ms  | ~673 ms  | ~3.9x slower |
| wide   | ~377.7 ms | ~5010 ms | ~13.3x slower | ~1126.8 ms | ~6455 ms | ~5.7x slower |

Root cause: `find_best_split` runs once per (feature, leaf) — millions of us-scale
calls; `rayon::join`'s fork/join + work-stealing per call dwarfs the work.

## Deviations from Plan

- **[Rule 1 — context correction] Production CPU SCAN path identified as the native
  path, not the rocm-gated fused kernel.** The plan's `<context>` named
  `build_fix_scan_resident_f64_on` (histogram.rs:2444) as the per-leaf hot path, but
  that function and `find_best_splits_fused_kernel` are `#[cfg(feature = "rocm")]`.
  On the CPU f64 anchor (the merge gate), `CpuBackend` uses the
  `find_best_splits_batched` trait default → `find_best_split_cpu_native`
  (split.rs:1355), a serial native Rust scan. The 2-lane lever was applied there —
  the actual code path the `SCAN_NS` counter measures. No behaviour change to the
  plan's intent; the lever targeted the correct hot path.
- **[Process] GO gate cleared but lever is a regression.** The plan front-loaded a
  NULL expectation "if SCAN < 20%". Here SCAN ≥ 20% (GO), so the variant was built
  and measured per the GO branch — and the measurement produced a NULL anyway
  (regression), which the plan also explicitly handles ("if parity holds AND a re-run
  shows a real warm latency reduction, document the win" — parity held, no win).
