<design_decision>
## P>1 forcing approach: (B) large real leaf — NOT (A) env mutation

Approach (B), a leaf of >=256k rows, is chosen. Justification + the load-bearing reason (A) is unsafe:

- `rowpart_target_cubes()` caches `LGBM_ROWPART_TARGET_CUBES` in a process-global `OnceLock`
  (histogram.rs:724-730), read ONCE per process. Under `cargo test` a single binary runs many
  rocm tests; if ANY resident-path test fires before this one, the OnceLock is already
  initialized and a `set_var("LGBM_ROWPART_TARGET_CUBES",...)` inside the test would be SILENTLY
  IGNORED — the test would run at the ambient target (possibly still P>1, but non-deterministically
  so), defeating the gate. Approach (A) is therefore fragile by construction, independent of the
  general env-leakage / `--test-threads` concern.
- Approach (B) mutates NO global state: with a >=256k-row leaf and `num_features < target`,
  the DEFAULT `row_partition_count` (target = CU-derived, fallback 64; min_leaf default 256_000)
  yields `clamp(target/num_features, 1, 16) > 1` with zero env dependence. It exercises REAL
  per-cube data across the multi-cube merge — the verifier's explicit recommendation
  (11-VERIFICATION.md WR-05 paragraph: ">=256k-row leaf ... confirm read-back still matches anchor").

Tradeoff (accepted): a bigger device buffer (~256k rows of binned u32 + f32 grad/hess, a few MB)
and a slower test (still seconds on the GPU). This is the cost of exercising the genuine multi-cube
path; throughput is irrelevant here (spoofed 8-CU APU — judge parity, not speed).

## Concrete sizing (must hold deterministically)
- `num_features = 3` (reuse the existing test's 3-feature spine: bins [4,3,5], mfb [2,0,1], offset [0,1,0]).
- `target` default >= `ROWPART_TARGET_CUBES_FALLBACK = 64` (and CU-derived is >= that on this box).
  With `num_features = 3 < target`, `row_partition_count(3, leaf_rows>=256_000) = clamp(target/3,1,16)`
  = 16 (since 64/3 = 21 clamped to 16, and any larger CU-derived target also clamps to 16). P = 16 > 1. ✓
- `leaf_rows` count must be `>= ROWPART_MIN_LEAF (256_000)`. Use `num_data = 300_000` rows and a leaf
  that selects ALL of them (or a contiguous >=256k subset) so `leaf_rows.len() >= 256_000`.
- Bin assignment for 300k rows: assign each row's bin via a cheap deterministic formula per feature
  (e.g. `row % num_bin` per feature) so every bin is populated and the fix/compact passes still fire.
  Gradients/hessians: small bounded deterministic values (e.g. `g = 0.25 + (i % 7) as f32 * 0.5`,
  `h = 1.0 + (i % 3) as f32`) so the overflow guard (`rows*max_abs*2^30 < i64::MAX`) is satisfied
  (300k * ~3.5 * 2^30 ~= 1.1e15 << 9.2e18). Keep |g|,|h| small.
</design_decision>
