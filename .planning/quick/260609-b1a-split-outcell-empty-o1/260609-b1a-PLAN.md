<objective>
Implement opportunity **O1** from 260609-aqy-ANALYSIS.md: allocate the 12-cell `out`
buffer via `client.empty(bytes)` (uninitialized) instead of `create_from_slice(T::as_bytes(&zeros))`
(host zero-alloc + upload) — for the TWO single-feature split launchers ONLY.

This is a parity-neutral micro-allocation cleanup, NOT a perf claim. The L3 finding
(round-trip is not the GPU bottleneck) means wall-clock impact is expected to be noise.
The point is removing a host alloc + tiny upload that the kernel makes redundant by
unconditionally overwriting all 12 cells. User explicitly requested implementation
despite the analysis's INVESTIGATE-FURTHER/not-now verdict.
</objective>

<safety_invariant>
Orchestrator pre-verified (do NOT skip re-confirming before editing):
- `find_best_split_kernel` (f64, launcher `find_best_split_*_on` at split.rs:797-833) and
  `find_best_split_kernel_f32` (launcher at split.rs:1676+) both launch a SINGLE unit
  (`CubeCount::Static(1,1,1)`, `CubeDim::new_1d(1)`).
- The shared `split_scan_body` (split.rs:144) has NO early `return` and writes ALL 12
  cells `out[ob+0..=11]` unconditionally at split.rs:372-383 (f64) / 605-616 (f32),
  using `=` assignment with sentinel values when no split is found — never `+=`.
- Therefore zero-init is NOT load-bearing for these two kernels; `empty()` is safe.

HARD EXCLUSIONS (touching any of these is a parity break — leave untouched):
- `find_best_splits_fused_kernel` / multi-feature batched launcher (split.rs:1263) —
  per-feature window writes `out[f*12..]`; a non-visited window would surface stale
  pooled memory. DO NOT change its `vec![0; ...]` allocation.
- ALL accumulate/atomic buffers in histogram.rs (the `histogram.rs:161-165` comment
  documents why empty() is unsafe there), subtract.rs, partition.rs.
</safety_invariant>
