# Quick Task 260609-eu9 — Plan

## Task

Implement Finding #1 from investigation 260609-eo5: parallelize the GPU partition
kernel. `data_partition_kernel` routed every row on a single lane (`UNIT_POS == 0`
loop, launched `CubeDim 1`); make it one-unit-per-row so the GPU uses all lanes.

## Why it is safe (parity)

Row routing is `route[i] = SplitInner(bins[i])` — per-row independent (no cross-row
carry) and integer-only, so there is no evaluation order to preserve (unlike the
histogram f64 fold). Each unit writes its own `route[i]` (disjoint, no atomics). The
order-dependent stable two-pass gather is already host-side and unchanged.

## Tasks

1. Rewrite `data_partition_kernel` (`crates/lgbm-compute/src/kernels/partition.rs`)
   to index by `ABSOLUTE_POS` with an `idx < bins.len()` bounds guard; move the
   scalar `th`/`default_to_right` setup inside the guard.
2. Update `data_partition_on` launcher to `CubeCount::Static(ceil(n/256),1,1)` ×
   `CubeDim::new_1d(256)` (mirrors the parallel histogram launcher).
3. Verify on BOTH runtimes: cubecl-cpu (unit tests) and the real gfx1100 hip path
   (`kernel_parity_partition_exact_on_hip`, bit-exact). Run the default merge gate.

## Done when

- `data_partition_kernel` is one-unit-per-row; launcher dispatches `ceil(n/256)` cubes.
- cubecl-cpu partition unit tests pass; default merge gate 0-failed.
- hip `kernel_parity_partition_exact_on_hip` passes (bit-exact routing on gfx1100).
- clippy clean on partition.rs.

## Scope guard

CpuBackend production uses `data_partition_cpu_native` (not the kernel) — untouched.
Decision: unified parallel kernel for all runtimes (matches the unified-kernel
preference) rather than a rocm-gated fork, since the op needs no atomics and
cubecl-cpu executes the multi-cube form correctly.
