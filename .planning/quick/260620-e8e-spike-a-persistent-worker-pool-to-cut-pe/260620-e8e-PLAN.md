<framing>
Bake the following into every task. Do NOT let the executor skip to integration.

1. **rayon ALREADY keeps threads alive.** The codebase uses the rayon 1.10 GLOBAL pool implicitly
   via `par_iter` — there is NO custom pool, crossbeam, or `ThreadPoolBuilder` anywhere. So the
   per-leaf fork/join cost is NOT thread spawn. It is `par_iter`'s work-splitting + the
   work-stealing **join barrier**. A custom pool only helps if its dispatch+barrier primitive is
   genuinely cheaper than rayon's join for N∈{20–80} tiny tasks. This is the whole hypothesis.

2. **The tree grows SEQUENTIALLY across leaves (leaf-wise).** Each leaf's scan must complete
   before the cross-feature argmax picks the next leaf to split. A persistent pool therefore
   CANNOT pipeline/overlap leaves — it can only make each leaf's SINGLE dispatch cheaper. Do NOT
   propose cross-leaf overlap; it is architecturally impossible here.

3. **Spin-wait vs block is the ship/no-ship axis.** A spin-wait-on-completion-atomic pool can have
   very low dispatch latency BUT burns cores continuously — including the sequential between-leaf
   gaps (argmax, data-partition, tree bookkeeping) AND whenever the library is loaded-but-idle
   (prediction-only, post-train). A blocking (condvar/park) pool avoids the burn but its wake
   latency reintroduces ≈ the fork/join cost we are trying to remove. This tradeoff MUST be
   measured and weighed: a pool that is faster but burns idle cores may still be a NO-SHIP for a
   library.

4. **dpk already proved** per-leaf fixed cost is ~99% fork/join + work, ≤0.6% alloc — so the
   dispatch primitive itself is the ONLY remaining lever, which is exactly what Task 1 tests.

**Honest expectation:** LIKELY a NULL. rayon's fork/join is highly optimized; leaves are
sequential (no pipelining); a spin-pool trades CPU burn for latency. A documented NULL at Task 1
(rayon's dispatch is already near-optimal / no primitive beats it by enough) is the expected,
fully-successful result.
</framing>

  (a) BASELINE — rayon `(0..N).into_par_iter().for_each(...)` over the GLOBAL pool (the exact
      primitive the fused per-leaf region uses today). This is the number to beat.
  (b) CANDIDATE-1 — a hand-rolled fixed-worker pool using ONLY std `std::thread` + atomics: N-1
      persistent worker threads parked on an `AtomicU64` "epoch"/"go" counter; the driver bumps
      the epoch to release them and SPIN-WAITS on an `AtomicUsize` completion counter for the
      join barrier. (Spin variant — the low-latency/high-burn end of the tradeoff.)
  (c) CANDIDATE-2 (optional, cheap to add) — either (i) the SAME hand-rolled pool but BLOCKING:
      workers `thread::park()` / driver `unpark` + a `Condvar`/`park` completion wait (the
      no-burn/higher-wake-latency end), OR (ii) rayon's own `ThreadPool::broadcast` /
      a pre-built `rayon::ThreadPool::install`. Pick whichever is fastest to wire; the goal is to
      bracket the spin-vs-block tradeoff with at least the spin candidate vs the rayon baseline.

Per-task work = a realistic per-feature scan proxy (~a few µs of trivial arithmetic over a small
fixed buffer, e.g. a tight fold over ~256–512 elements) so the dispatch cost is measured against
real task granularity, NOT a no-op (a no-op overstates the relative dispatch share). Also include
a pure no-op row as a dispatch-floor reference.
