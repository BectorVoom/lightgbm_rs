# Spike Manifest

## Idea

Optimise lightgbm_rs **learning (train) speed**, both ends of the row-count curve:
- **High rows (GPU track, spike 001):** the ROCm path is launch-bound and ~100× slower
  on small data; prove where it crosses below the CPU anchor at scale. → ~700k rows.
- **Low rows (CPU track, spike 002):** the CPU anchor is ~2–3× off C++ even where it's
  closest; localize the fixed per-iteration gap via a per-phase A/B. → histogram build.
See `.planning/notes/gpu-track-goal-crossover-at-scale.md` and
`.planning/notes/low-row-gap-fixed-per-iteration-overhead.md`.

## Requirements

- Backend stays **compile-time switched** (`--features rocm`); the CPU f64 anchor
  remains the default and the bit-exact merge gate. Speed work must not touch parity.
- "GPU is faster" is only claimed in the regime the data supports — never route
  small/medium datasets to the GPU.
- Crossover claims are wall-clock facts; the ~1e-6 GPU-vs-CPU parity contract at large
  shapes is a separate, still-open gate.
- **`Vec<Vec<T>>` is not categorically a pessimization** (spikes 010/011). The
  discriminator is *usage*: a `vec![template; n]`-style structure rebuilt on the hot
  path is waste → flatten (010, shipped); a per-thread private accumulator written
  once + merged once is already optimal → keep it, flattening it forces shared-buffer
  false sharing (011, regressed 13–21%). Do not "tidy" the parallel build's
  per-feature `Vec<Vec<f64>>` in `build_histograms_into` — a NOTE marks it load-bearing.
- **GPU large-data attribution is measured, not assumed** (spike-014). At the wide
  shape (1M×500) GPU train wall-clock is ≈ ⅓ redundant resident-bin re-upload, ⅓
  growth-phases (scan-fused kernel + partition), ⅙ binning (bench artifact), ⅙ loop
  overhead. The histogram kernel is NOT the dominant cost. Profiling needs the
  `LGBM_PHASE_PROF=1` whole-train BUDGET (not just the growth-phase split, which folds
  the GPU kernel into "scan" via resident fusion and covers <½ the clock). Pending
  build lever: **hoist `upload_resident_bins` (learner.rs:826) out of the per-tree
  `train_inner` to once-per-train** — the bins are immutable, so re-uploading 2GB every
  tree is pure waste (≈−31% wall-clock at 1M×500, parity-neutral). [SHIPPED quick-p9v.]
- **Post-p9v, the wide-shape (×500) GPU bottleneck is the f32-atomic histogram BUILD**
  (spike-015), NOT the kernel-of-record, the upload, or the scan round-trip. The
  `phase_prof` "scan=96%" is an ASYNC ARTIFACT: the build launches un-synced, so its
  device-compute materializes inside the scan's `read_one_unchecked`. A forced pre-scan
  drain (`LGBM_SCAN_DRAIN=1`) re-attributes it: **build 86%→92% (GROWS with rows)**, scan
  launch+readback 14%→8% (shrinks), marshal+upload ~0%. Build is atomic-contention-bound
  (~820 Mr/s), ALREADY f32-atomic + LDS-privatized; spike-007 row-partition is inactive
  at wide (`768/500=1` → P=1). **Measured DEAD levers — do NOT pursue: scan-round-trip
  batching, constant-array hoisting, f32 build switch (already done).** At 250k×500 the
  CPU anchor (1.80s) beats the GPU (7.14s) ~4× ⇒ **wide-many-feature shapes route to
  CPU.** Only untried build lever = finer (per-warp) LDS sub-histogram privatization.
- **Post-021 the GPU bottleneck is REGIME-SPLIT (spike-023, the re-profile kill-check).**
  Per-tree (shape-independent @ num_leaves=31): ~30 build + ~29 subtract + **~59 scan-
  readback SYNCS = ONE per leaf-node** (both siblings of every split scanned in TWO
  separate launches+readbacks) = ~118 device launches. The histogram **subtraction trick
  ALREADY runs on-device** (`subtract_resident`, no double-rebuild) — that lever is closed.
  DRAIN attribution: **launch-bound (small/medium)** = the scan-readback SYNC floor is the
  largest reclaimable residual (~48%/35% of the scan round-trip); **compute-bound
  (large/wide)** = build-compute dominates and GROWS with rows (68%→96.5%@1M×500; the u64
  win made atomics cheaper, not the build smaller), scan-sync → 3.2%. Host `partition`
  (single-threaded `DataPartition::split`) grows to 23% — a CPU-track residual no GPU lever
  touches. Build levers are exhausted on this APU; wide routes to CPU. Re-profile after
  EVERY build change — the bottleneck has now moved three times (014→015→023).
- **Sibling-scan co-pack is VALIDATED + bit-exact and SLATED TO WIRE (spike-024).** Co-pack
  the two siblings of every split into ONE scan launch+readback (59→~30 syncs/tree) =
  sign-stable **~2.0× isolated** (parity OK every cell; the per-feature sequential scan is
  unchanged — no spike-016 reorder). Honest e2e = **~10–15% small/medium, ~1.5% wide**
  (co-pack halves the sync COUNT, reclaiming ~½ the genuine scan-sync per 023; the
  cold-isolated 2× overstates warm). **NEXT BUILD (user chose WIRE):** 2-slot production
  scan kernel (two Handles, 2×n SplitInfos, one readback) + growth-loop reorder (defer the
  smaller-child scan past `subtract_resident` — both Handles are already co-resident there)
  + oracle parity re-pin. Plan via `/gsd-plan-phase`. **▶ SHIPPED** (Phase 12, default-ON).
- **Post-(024+029)-SHIPPED the bottleneck MOVED a 4th time, regime-specifically (spike-034,
  the re-profile kill-check; 2 restarts sign-stable).** 024 + 029 are both LIVE and verified in
  production (co-pack `scan_resident` **59→30 syncs/tree**, ~9–11% e2e at large; narrow-width
  device partition). **LAUNCH-BOUND (small/med/large):** the spike-023 per-leaf scan-sync floor
  is CLOSED — scan is now **3.0%/7.0%** of train (med/large), and the NEW #1 reclaimable phase is
  **partition: 38% (med) / 30% (large)** = the device `data_partition_native` round-trip (~30
  per-split blocking readbacks/tree; 029 cut bytes not the round-trip). **WIDE/compute-bound:**
  UNCHANGED — `hist+split≈91%` (build-compute, uncoalesced-gather-bound per 030), partition ~9%,
  scan-sync tiny; neither lever targets it (predicted). The recommended next lever (035, NOT
  built): **route partition to the HOST on the rocm backend** (the SHIPPED spike-027 fused-gather
  host partition — no device round-trip/sync), measuring the resident-build index re-upload
  tradeoff; ROI-gated (this APU loses to CPU overall; real payoff on discrete gfx110x).
  **Tooling debt → FIXED (quick-260625-tw1, commit `128a4c2`):** the `LGBM_SCAN_DRAIN` build-drain
  was missing on the co-pack path (Phase 12 routed through a separate siblings fn); restored +
  GPU-verified (build_drain 0%→97.5/98.6% medium/large under `LGBM_SCAN_PROF=1 LGBM_SCAN_DRAIN=1`).
  Correct invocation needs `LGBM_SCAN_PROF=1` too; read `SCAN_DRAIN_NS`, not phase_prof `build`.
