# Spike Manifest

## Idea

Optimise lightgbm_rs **learning (train) speed**, both ends of the row-count curve:
- **High rows (GPU track, spike 001):** the ROCm path is launch-bound and ~100× slower
  on small data; prove where it crosses below the CPU anchor at scale. → ~700k rows.
- **Low rows (CPU track, spike 002):** the CPU anchor is ~2–3× off C++ even where it's
  closest; localize the fixed per-iteration gap via a per-phase A/B. → histogram build.
See `.planning/notes/gpu-track-goal-crossover-at-scale.md` and
`.planning/notes/low-row-gap-fixed-per-iteration-overhead.md`.

## Requirements

- Backend stays **compile-time switched** (`--features rocm`); the CPU f64 anchor
  remains the default and the bit-exact merge gate. Speed work must not touch parity.
- "GPU is faster" is only claimed in the regime the data supports — never route
  small/medium datasets to the GPU.
- Crossover claims are wall-clock facts; the ~1e-6 GPU-vs-CPU parity contract at large
  shapes is a separate, still-open gate.
- **`Vec<Vec<T>>` is not categorically a pessimization** (spikes 010/011). The
  discriminator is *usage*: a `vec![template; n]`-style structure rebuilt on the hot
  path is waste → flatten (010, shipped); a per-thread private accumulator written
  once + merged once is already optimal → keep it, flattening it forces shared-buffer
  false sharing (011, regressed 13–21%). Do not "tidy" the parallel build's
  per-feature `Vec<Vec<f64>>` in `build_histograms_into` — a NOTE marks it load-bearing.
- **GPU large-data attribution is measured, not assumed** (spike-014). At the wide
  shape (1M×500) GPU train wall-clock is ≈ ⅓ redundant resident-bin re-upload, ⅓
  growth-phases (scan-fused kernel + partition), ⅙ binning (bench artifact), ⅙ loop
  overhead. The histogram kernel is NOT the dominant cost. Profiling needs the
  `LGBM_PHASE_PROF=1` whole-train BUDGET (not just the growth-phase split, which folds
  the GPU kernel into "scan" via resident fusion and covers <½ the clock). Pending
  build lever: **hoist `upload_resident_bins` (learner.rs:826) out of the per-tree
  `train_inner` to once-per-train** — the bins are immutable, so re-uploading 2GB every
  tree is pure waste (≈−31% wall-clock at 1M×500, parity-neutral).
